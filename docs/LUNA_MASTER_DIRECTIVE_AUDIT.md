# Helmetsan Master Directive

## Executive position

The audit identifies five separate production issues that are interacting:

1. **The catalog is not losing 969 canonical products; it contains 969 additional published rows outside valid translation clusters.**
2. **Polylang relationship writes are non-atomic and were performed after post insertion, allowing retries to create additional rows.**
3. **The theme is only partially internationalized.** Product body fields are more mature than global UI, archives, cards, and editorial pages.
4. **Metadata key presence has been mistaken for metadata quality.** Placeholder media, English JSON, untranslated SEO titles, and leaked Markdown are data-quality failures.
5. **Caching and bot controls are incomplete outside `/helmets/`, while current rate limits are too permissive for abusive traffic.**

The remediation must be staged. Do not perform bulk deletion, direct taxonomy manipulation, or broad cache-rule changes against production without backups, a canary cohort, redirect mapping, and rollback evidence.

# 1. Orphaned duplicate cleanup and translation-cluster healing

## 1.1 Exact mathematical diagnosis

The per-language relationship is:

\[
O_L = T_L - C_L
\]

Where:

- \(T_L\) = published `helmet` posts assigned to language \(L\)
- \(C_L\) = posts participating in a valid Polylang translation cluster
- \(O_L\) = language-assigned posts not participating in a valid cluster

| Language | Total \(T_L\) | Clustered \(C_L\) | Orphans \(O_L\) |
|---|---:|---:|---:|
| EN | 9,849 | 9,849 | 0 |
| DE | 9,924 | 9,808 | 116 |
| ES | 9,811 | 9,770 | 41 |
| FR | 10,223 | 9,772 | 451 |
| IT | 9,860 | 9,851 | 9 |
| JA | 9,841 | 9,823 | 18 |
| NL | 9,809 | 9,798 | 11 |
| PL | 9,823 | 9,812 | 11 |
| PT | 9,829 | 9,822 | 7 |
| ZH | 10,115 | 9,810 | 305 |
| **Total** | **99,204** | **98,235** | **969** |

The total is therefore:

\[
99,204 - 98,235 = 969
\]

The three largest discrepancies are:

\[
FR - EN = 10,223 - 9,849 = 374
\]

\[
ZH - EN = 10,115 - 9,849 = 266
\]

\[
DE - EN = 9,924 - 9,849 = 75
\]

Those differences are not identical to the orphan counts because the clustered catalog is not perfectly uniform by language. Some legitimate translation clusters may be incomplete, and the EN count is not automatically the canonical count for every locale.

The correct conclusion is:

- **FR contains 451 orphan rows.**
- **ZH contains 305 orphan rows.**
- **DE contains 116 orphan rows.**
- These are the principal sources of excess published rows.
- The remaining language counts reflect normal translation completeness variation plus smaller orphan populations.

The root failure is a classic distributed retry race:

1. Worker A checks for a product.
2. Worker B checks for the same product before A commits.
3. Both see no existing translated post.
4. Both insert a new post row.
5. Both assign the language term.
6. One or both workers time out or fail before writing the translation-group relationship.
7. The retry inserts another row.
8. The result is a published post with a language but no valid translation cluster.

A language taxonomy term is not proof of cluster membership. A valid record must have:

- a valid post ID;
- the expected `post_type`;
- `post_status = publish`, unless intentionally staged;
- exactly one intended language;
- a stable source/product identity;
- a valid translation-group membership;
- no conflicting canonical identity.

## 1.2 First create a forensic inventory

Before changing anything, create an immutable export containing:

- post ID;
- `post_name`;
- `post_date`;
- `post_modified`;
- language;
- translation group identifier;
- `_helmet_unique_id`;
- source/import ID;
- SKU or GTIN, if available;
- canonical URL;
- title;
- `post_parent`;
- attachment references;
- inbound internal-link count;
- external-link count if available;
- indexed status from GSC where available;
- Yoast canonical;
- redirect destination candidate;
- duplicate fingerprint.

Do not use title equality as the primary duplicate key. Use this priority order:

1. Stable upstream product ID.
2. `_helmet_unique_id`.
3. SKU/GTIN.
4. Manufacturer + model + normalized shell size or variant.
5. Canonical source URL.
6. Normalized content fingerprint as a last-resort review signal.

A recommended fingerprint is:

```text
sha256(
  manufacturer
  + "\x1f"
  + model
  + "\x1f"
  + variant
  + "\x1f"
  + normalized_unique_id
)
```

Never merge merely because two products have similar titles.

## 1.3 Classify every orphan

Every orphan should be placed into one of four classes:

### Class A: Exact duplicate of a valid localized post

Evidence:

- same stable product identity;
- same language;
- same product variant;
- one row is clearly newer or was generated by the failed worker;
- no unique editorial content that must be preserved.

Action:

- select the surviving post;
- map orphan URL to survivor URL with a permanent redirect;
- transfer only verified metadata or attachments;
- delete or trash the orphan after redirect deployment.

### Class B: Valid translation missing from an existing group

Evidence:

- same product identity as an existing product in another language;
- localized content is materially useful;
- no same-language collision;
- post is not merely an exact retry.

Action:

- attach it to the correct translation group using the supported Polylang API or controlled administrative operation;
- verify exactly one post per language in the group;
- regenerate hreflang and sitemap output.

### Class C: Unique product accidentally classified as orphan

Evidence:

- no matching canonical product;
- unique SKU or product identity;
- useful content and valid media.

Action:

- create or locate the correct translation group;
- make the post the canonical member for its language;
- create missing translations only through the normal ingestion pipeline.

### Class D: Invalid, empty, placeholder, or malicious row

Evidence:

- placeholder media;
- no stable product identity;
- duplicate content;
- broken source record;
- spam or test content;
- no meaningful inbound value.

Action:

- quarantine first;
- set `noindex` if it must remain temporarily accessible;
- then return `410` or redirect to the most relevant surviving product;
- delete only after the redirect/noindex plan is live.

## 1.4 Safe healing sequence

### Phase 0: Freeze unsafe writers

Temporarily disable all non-idempotent import and translation workers. Permit reads and controlled manual repair only.

### Phase 1: Database protection

Take:

- full MariaDB backup;
- binlog position capture;
- `wp_posts`, `wp_postmeta`, taxonomy, term relationship, and Polylang-related table backups;
- exported URL inventory;
- current sitemap and redirect configuration.

Test restoration on a separate MariaDB instance.

### Phase 2: Build a repair table

Create a dedicated table, not a transient spreadsheet:

```sql
CREATE TABLE wp_helmet_repair_queue (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    orphan_post_id BIGINT UNSIGNED NOT NULL,
    survivor_post_id BIGINT UNSIGNED NULL,
    source_key VARCHAR(191) NULL,
    orphan_lang VARCHAR(16) NOT NULL,
    action ENUM('RECLUSTER','REDIRECT_DELETE','KEEP','REVIEW','IGNORE') NOT NULL DEFAULT 'REVIEW',
    confidence DECIMAL(5,4) NOT NULL DEFAULT 0,
    old_url TEXT NULL,
    new_url TEXT NULL,
    status ENUM('PENDING','LOCKED','APPLIED','VERIFIED','FAILED') NOT NULL DEFAULT 'PENDING',
    reason TEXT NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_orphan (orphan_post_id)
);
```

Populate this table from read-only forensic queries and deterministic matching rules.

### Phase 3: Re-cluster before deleting

For Class B records:

1. Lock the repair row.
2. Confirm both posts still exist and have not changed materially.
3. Confirm no same-language collision in the target group.
4. Confirm the post has the expected language term.
5. Use the supported Polylang integration to save the complete translation map.
6. Re-read the relationship and verify it.
7. Regenerate or invalidate any translation caches.
8. Mark the repair row `VERIFIED`.

Do not directly write serialized Polylang relationship data unless the exact installed Polylang version and storage model have been verified. Polylang internals and APIs can change. A direct SQL update can create a group that appears valid in one table but is inconsistent with Polylang’s caches or term relationships.

### Phase 4: Redirect and retire duplicates

For Class A and D records:

1. Record the old permalink.
2. Select the destination URL.
3. Deploy a redirect before deletion.
4. Keep the redirect active for at least 12 months for high-value URLs.
5. Remove the orphan from XML sitemaps.
6. Purge page caches.
7. Verify the old URL returns the intended `301` or `410`.
8. Trash or delete in controlled batches.
9. Recheck internal links and hreflang.

Do not redirect every duplicate to the language homepage. Redirect to the exact surviving product where a confident mapping exists; otherwise use `410` for genuinely invalid rows.

### Phase 5: Controlled batch size

Use small batches:

- 25–100 records per transaction;
- maximum one language at a time;
- FR and ZH first because they contain the largest populations;
- a canary batch of 10 records;
- post-batch validation before continuing.

Monitor:

- 404 rate;
- redirect rate;
- sitemap URL count;
- GSC indexed pages;
- Polylang cluster integrity;
- database lock waits;
- PHP-FPM latency.

## 1.5 Permanent atomic ingestion design

### Required database invariant

Create an ingestion identity table with a unique key:

```sql
CREATE TABLE wp_helmet_ingest_identity (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    source_system VARCHAR(64) NOT NULL,
    source_product_key VARCHAR(191) NOT NULL,
    language VARCHAR(16) NOT NULL,
    post_id BIGINT UNSIGNED NULL,
    payload_hash CHAR(64) NOT NULL,
    state ENUM('PROCESSING','COMMITTED','FAILED') NOT NULL DEFAULT 'PROCESSING',
    lease_until DATETIME NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_source_lang (source_system, source_product_key, language),
    KEY ix_lease (state, lease_until)
) ENGINE=InnoDB;
```

The unique key is the real protection. A distributed lock alone is not sufficient.

### Transactional worker pattern

1. Normalize the upstream product identity.
2. Begin an InnoDB transaction.
3. Execute `INSERT ... ON DUPLICATE KEY UPDATE`.
4. If an existing committed row is found, return its post ID and stop.
5. If a lease is active, do not create another post.
6. If the lease expired, atomically take over the lease.
7. Create or update the post.
8. Assign the language.
9. Save the translation-group relationship.
10. Update the identity row to `COMMITTED`.
11. Commit.
12. Only then enqueue media processing, indexing, or secondary enrichment.

Use a row lock:

```sql
SELECT *
FROM wp_helmet_ingest_identity
WHERE source_system = ?
  AND source_product_key = ?
  AND language = ?
FOR UPDATE;
```

A MySQL advisory lock may be added:

```sql
SELECT GET_LOCK(CONCAT('helmetsan:helmet:', ?), 10);
```

But `GET_LOCK()` must not be the only guard. It is connection-scoped, can be lost when the connection drops, and does not replace a unique database constraint.

For Python, use a connection-level transaction and explicit lock ownership. For PHP, use `$wpdb` with an InnoDB transaction where possible. Never hold a database lock while making remote API calls. Reserve the row, commit the lease, perform bounded work, then finalize in a second transaction.

# 2. Native multilingual theme remediation

## 2.1 Theme architecture

Separate all user-facing text into four categories:

### A. Static theme UI

Examples:

- “Buy Now”
- “Compare”
- “Safety”
- “Clear All”
- “Sort by”
- “Recommended”
- “Page”

Use WordPress gettext:

```php
esc_html_e( 'Buy Now', 'helmetsan' );
echo esc_html__( 'Compare', 'helmetsan' );
printf(
    esc_html__( '%s results', 'helmetsan' ),
    number_format_i18n( $count )
);
```

Use:

- `esc_html__()` for text;
- `esc_attr__()` for attributes;
- `wp_kses_post()` only for explicitly permitted translated HTML;
- `esc_url()` for URLs;
- translator comments for ambiguous strings.

### B. Polylang-managed editorial strings

Examples:

- region-specific buying-guide introductions;
- merchandising labels managed by administrators;
- local campaign copy;
- footer trust messages.

Register once:

```php
add_action( 'admin_init', function () {
    if ( function_exists( 'pll_register_string' ) ) {
        pll_register_string(
            'comparison_empty_state',
            'Select helmets to compare',
            'Helmetsan Theme',
            false
        );
    }
} );
```

Retrieve safely:

```php
$text = function_exists( 'pll__' )
    ? pll__( 'Select helmets to compare' )
    : __( 'Select helmets to compare', 'helmetsan' );

echo esc_html( $text );
```

Do not call `pll_register_string()` during front-end rendering. Registration belongs in an admin or deployment synchronization phase.

### C. Product and editorial content

Use translated post fields and translated custom fields. Do not run every product description through gettext.

### D. Numeric and regional values

Do not translate currency, dimensions, ratings, or certification codes as ordinary strings. Store structured values and format them by locale and market.

Generate a POT file in CI and fail builds when new user-facing literals are introduced without translation extraction.

Use a string inventory with:

- source file;
- line number;
- text domain;
- context;
- translator comment;
- status per language.

## 2.3 Performance at 100,000 posts

Gettext translation lookup is not the performance bottleneck if implemented correctly.

Rules:

- load the text domain once;
- use compiled MO files;
- do not call Polylang registration on the front end;
- avoid repeated `get_option()` calls inside loops;
- cache market configuration in a persistent object cache;
- use one query for archive filter options;
- avoid per-card translation-group lookups;
- pass already-resolved labels into template parts;
- use `wp_cache_get()` for repeated product metadata;
- avoid loading every translation of every product merely to render one archive.

For cards, query only required fields and meta. Use a dedicated read model or indexed lookup for large archives if necessary.

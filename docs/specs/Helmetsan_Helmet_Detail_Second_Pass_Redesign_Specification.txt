HELMETSAN — SECOND-PASS PRODUCT / HELMET DETAIL PAGE REDESIGN SPECIFICATION

DOCUMENT PURPOSE

This is the revised and more thorough Helmetsan product-page redesign
context after reviewing the latest three full-page screenshots supplied
for:

1.  Pioneer
2.  Storm
3.  X3000

This document supersedes and expands the earlier Helmetsan redesign
context.

The goal is NOT simply to make the current product page prettier.

The goal is to turn the helmet detail page into the core “helmet
intelligence” experience of Helmetsan.

The page should help a rider move from:

“I found this helmet”

to:

“I understand what it is -> I understand its safety -> I understand fit
-> I understand what I am getting -> I know where to buy it -> I can
compare it -> I understand compatible accessories -> I know how
trustworthy the data is.”

The implementation is expected to be done using Antigravity IDE with
Gemini 3.6. This document is written so that Gemini can be given it as
implementation context.

IMPORTANT: The current screenshots reveal that several problems are no
longer just visual. There are data integrity, content hierarchy, image
pipeline, component consistency, empty-state and information
architecture problems. These must be treated separately from styling
problems.

==================================================================== 1.
CORE PRODUCT POSITIONING
====================================================================

Helmetsan is positioned as:

GLOBAL HELMET INTELLIGENCE PLATFORM

It should feel closer to a technical intelligence / research platform
than a conventional ecommerce catalog.

The strongest product promise is:

“Help the rider make a better helmet decision.”

The product page therefore should not optimize for: - maximum number of
boxes - maximum amount of specification text - maximum number of product
cards - artificial ratings - generic ecommerce conversion patterns

It should optimize for: - decision clarity - trustworthy data - safety
understanding - fit understanding - comparison - verified
compatibility - purchase discovery - source transparency

A helmet detail page is the most important page in the entire
information architecture because it is the place where all the other
Helmetsan entities converge.

HELMET -> BRAND -> SAFETY STANDARDS -> CERTIFICATIONS -> FIT / SIZING ->
SPECIFICATIONS -> RETAILERS -> PRICE HISTORY -> REVIEWS -> ACCESSORIES
-> SIMILAR HELMETS -> MOTORCYCLES / USE CASES -> SOURCES

The detail page should make those relationships useful rather than
merely displaying them.

==================================================================== 2.
SECOND-PASS SCREENSHOT AUDIT
====================================================================

Three new screenshots were reviewed.

The pages are visually more organized than the earlier version, but the
screenshots expose a number of systemic problems.

The most important conclusion is:

THE TEMPLATE IS IMPROVING, BUT THE PAGE IS STILL A DATABASE RECORD
WRAPPED IN CARDS.

It has not yet become a decision-support experience.

The page currently has: - a large title area - tabs - large image
region - price / buy panel - quick facts - overview - buying section -
product concept/specifications - compare - reviews - accessories - more
from brand - data verification - footer

That is directionally correct.

However: - the hero does not work because product imagery is missing -
the buy panel appears insufficiently tied to actual product data - the
information hierarchy remains weak - many sections have excessive empty
space - safety is not prominent enough - fit is not prominent enough -
data provenance is too far down - empty states consume too much vertical
space - cards dominate the visual language - product recommendation
logic is not visible - similar products are weakly differentiated -
accessory cards have image failures - the page is extremely long
relative to the information density - the page contains repeated
patterns without enough editorial hierarchy - the same visual template
is being used for products with very different levels of data
completeness

This last point is critical.

A product with: - strong certification data - multiple retailers - real
images - real reviews - real specs

should not look exactly the same as a product with: - one image - sparse
specs - no reviews - no price history - no verified fit data.

The UI needs DATA-AWARE STATES.

==================================================================== 3.
P0 FINDINGS — MUST FIX BEFORE POLISH
====================================================================

P0 means these should be treated as correctness, trust or core UX
problems.

  ----------------------------
  P0.1 PRODUCT IMAGE FAILURE
  ----------------------------

All three screenshots show a large product image area that appears
empty/broken/unusable.

This is the single most damaging visual problem.

The hero is supposed to be the visual anchor of the product page.

Instead the user sees a large white area with an image failure.

This creates several negative impressions: - product may not exist -
database may be incomplete - site may be unreliable - page may be
unfinished - user cannot visually confirm what product they are looking
at

The solution is NOT to simply make the empty area smaller.

First fix the underlying image pipeline.

Investigate: - image URL - database image field - CDN URL -
WordPress/media URL if applicable - image transformation - lazy
loading - CORS - hotlink protection - URL encoding - file existence -
MIME type - responsive srcset - frontend mapping - fallback image
component

Add logging for: product ID image URL HTTP response fallback reason

The UI should reserve image dimensions so that a missing image does not
create layout shifts.

If there is one valid image: show it prominently.

If multiple valid images: show: - main image - thumbnails - image
count - zoom/fullscreen

If no image: show a deliberate branded placeholder:

IMAGE UNAVAILABLE

with: “Helmetsan does not currently have a verified product image for
this model.”

Do NOT show: - browser broken-image icon - random helmet image - another
model’s image - generic unrelated stock photo

Never substitute a different product image simply because the brand or
model name is similar.

  ----------------------------------------
  P0.2 PRICE / BUY DATA MUST BE VERIFIED
  ----------------------------------------

The three screenshots show a very similar price treatment and appear to
reuse values/patterns.

This must be audited carefully.

The page should never display a generic “Best Current Price” if the
value is not actually associated with the current helmet.

The data relationship must be:

helmet_id -> retailer offers -> current price -> availability ->
shipping -> last checked

Do not calculate a best price from unrelated records.

The UI should distinguish:

PRICE ₹XX,XXX

from:

BEST CURRENT OFFER ₹XX,XXX

and:

PRICE LAST CHECKED date/time

If no current price: “Price unavailable”

If stale: “Last checked X days ago”

If multiple currencies: use the selected market/currency.

If India: ₹

If United States: $

The currency selector in the header should actually affect price
rendering consistently.

  ---------------------------------------------------------------------------
  P0.3 MISSING IMAGE PIPELINE ALSO AFFECTS ACCESSORIES AND SIMILAR PRODUCTS
  ---------------------------------------------------------------------------

The product page has additional cards later in the page where images
appear missing or weak.

This is not an isolated hero problem.

The site appears to have a systemic product-image problem.

Fix the shared ProductImage component rather than fixing individual
pages.

Create one reusable image system with states:

LOADING AVAILABLE MISSING ERROR UNVERIFIED

Example:

The same component should be used for: - helmets - accessories - brands
where applicable - related products

  ----------------------------------------------------------
  P0.4 ZERO-REVIEW RATING MUST NOT LOOK LIKE A REAL RATING
  ----------------------------------------------------------

The older version showed “0.0” in the reviews section.

The revised version is moving toward a “No verified rider reviews yet”
state, which is much better.

Keep this rule permanently.

If there are zero reviews:

NO VERIFIED RIDER REVIEWS YET

Do not show: 0.0 / 5 0 stars empty rating bars that look like a bad
rating

Because 0 reviews is not the same as a 0 rating.

When reviews exist: show actual rating and sample size.

Example: 4.3 128 rider reviews

Never infer rating from missing data.

  ----------------------------------------------
  P0.5 FAKE / PLACEHOLDER DATA MUST BE REMOVED
  ----------------------------------------------

The screenshots contain areas where values, ratings, badges or product
information can look authoritative even when the underlying dataset
appears incomplete.

Audit all of these.

Potentially problematic examples: - generic safety scores - generic “95”
type ratings - generic “premium” positioning - generic safety focus
percentages - generic review values - generic compatibility - generic
product scores - generic popularity - hardcoded country/origin -
hardcoded price - hardcoded retailer information

Every visible number needs a source.

If a metric has no methodology: remove it.

If a metric has a methodology: show an explanation.

Helmetsan should prefer: “Verified ECE 22.06” over: “Safety Score 95”

unless a legitimate scoring system exists.

==================================================================== 4.
P0 DATA MODEL PROBLEM
====================================================================

The product page currently appears to be assembled from multiple
independent blocks.

This makes it easy for: - title to come from one record - price from
another - image from another - certification from another - related
products from a generic query - accessories from a broad brand query

The result can look correct while being logically wrong.

The canonical product model should be:

Helmet - id - brand_id - name - model_number - slug - helmet_type -
description - status - introduced_at - discontinued_at - images[] -
certifications[] - standards[] - specifications{} - fit{} -
accessories[] - retailers[] - price_history[] - reviews[] -
related_helmets[] - sources[] - last_verified_at

Every child relationship must be keyed to the helmet ID, not inferred
from: - brand - text search - model name similarity - image similarity

==================================================================== 5.
ABOVE-THE-FOLD REDESIGN
====================================================================

The current hero is structurally better than before but still too weak.

The first screen needs to answer:

WHAT IS IT? IS IT SAFE? WHO IS IT FOR? WHAT DOES IT COST? WHERE CAN I
BUY IT?

Suggested structure:

  --------------------------------------------------
  BREADCRUMB

  BRAND PRODUCT NAME

  Helmet type • certification • key use

  [ IMAGE / GALLERY ] [ DECISION PANEL ]

  HELMETSAN QUICK VERDICT

  Best for: • …

  Consider: • …

  Certification: ✓ ECE 22.06

  Best current price: ₹XX,XXX

  [ WHERE TO BUY ] [ COMPARE ]
  --------------------------------------------------

Do not put every fact into a card.

Use hierarchy.

The title should be large enough.

Brand should be clearly secondary.

Product type should be visible immediately.

Certification should be one of the strongest metadata signals.

==================================================================== 6.
QUICK VERDICT — MAKE THIS THE SIGNATURE HELMETSAN FEATURE
====================================================================

The current page lacks a strong “why this matters” layer.

Create:

HELMETSAN QUICK VERDICT

Possible sections:

BEST FOR - Daily commuting - Street - Touring

ONLY IF SUPPORTED BY DATA.

KEY STRENGTHS - Verified certification - Actual feature - Actual
construction benefit

CONSIDER - Actual limitation - Missing information - Fit uncertainty

NOT RECOMMENDED FOR Only if there is verified evidence supporting the
statement.

Do not turn this into an arbitrary AI score.

The value of the feature is explanation.

Example:

BEST FOR Daily street riding

WHY ECE 22.06 certification, full-face construction and available
ventilation data.

CONSIDER Head-shape information has not been verified.

That is much more useful than: “92/100”.

==================================================================== 7.
PRODUCT STATUS / DATA COMPLETENESS
====================================================================

Add a compact data-quality indicator.

Example:

DATA STATUS Verified across 7 sources Last verified 12 Aug 2026

Or:

DATA STATUS Partially verified 3 of 8 key fields confirmed

This is more valuable than fake precision.

Potential completeness categories:

VERIFIED MOSTLY VERIFIED PARTIALLY VERIFIED LIMITED DATA

Never punish a product with an arbitrary “score”.

==================================================================== 8.
QUICK FACTS — CURRENT VERSION IS TOO FLAT
====================================================================

The quick facts section is directionally good.

However, all facts currently have similar visual weight.

The system should identify:

PRIMARY FACTS - Certification - Helmet type - Weight - Shell material -
Retention

SECONDARY FACTS - Visor - Sun visor - Pinlock - Ventilation -
Communication compatibility

Only render fields that exist.

If certification is unknown: do not create an empty “Certification”
card.

Instead: Certification Not verified

This makes missing information explicit.

==================================================================== 9.
PRODUCT OVERVIEW — REDUCE THE BOXINESS
====================================================================

The overview section currently contains a text block plus several
right-side boxes.

It still feels like a dashboard.

Redesign as:

ABOUT THE HELMET

Short editorial summary.

Then a compact “At a glance” list.

Example:

Construction Polycarbonate

Helmet type Full Face

Retention Double D-ring

Certification ECE 22.06

This can be a two-column technical list rather than multiple floating
cards.

The content should be easy to scan.

==================================================================== 10.
SAFETY NEEDS TO MOVE UP
====================================================================

Safety is Helmetsan’s strongest differentiator.

It should not feel like just another specification.

Recommended order after hero:

Quick Facts Safety Snapshot Fit & Sizing Specifications

rather than burying safety inside a long technical section.

Safety Snapshot should contain:

CERTIFICATION ECE 22.06 Verified

STANDARD European regulation

ROTATIONAL TESTING Verified / Not specified

IMPACT TESTING Verified / Not specified

SOURCE View source

Every item must be driven by real data.

Clicking a standard should lead to the Safety Standards page.

==================================================================== 11.
SAFETY LANGUAGE MUST BE PRECISE
====================================================================

Avoid statements like:

“5-star safety”

unless that is specifically the SHARP rating.

Do not combine: - DOT - ECE - ISI - SHARP - Snell

into a generic safety score.

These are different systems with different roles.

Use:

CERTIFICATION ECE 22.06

SHARP 4/5

only when the actual product has verified SHARP data.

If SHARP has not tested the helmet: “SHARP rating: Not tested / not
available”

Do not say: “0/5”.

==================================================================== 12.
FIT & SIZING — THIS IS CURRENTLY UNDERDEVELOPED
====================================================================

Fit is one of the most important helmet decisions.

The page should have a dedicated:

FIT & SIZING

Show:

SIZE RANGE S / M / L / XL

HEAD CIRCUMFERENCE XX–XX cm

HEAD SHAPE Intermediate Oval ONLY if verified.

SHELL SIZES 2 shell sizes ONLY if verified.

LINER Removable / Fixed ONLY if verified.

Then:

HOW TO MEASURE

Simple 3-step guide.

Potential future: interactive head measurement.

Important:

Do not infer head shape from: - product photo - brand - helmet type -
generic manufacturer reputation

If unknown:

HEAD SHAPE Not verified

This is better than false certainty.

==================================================================== 13.
SPECIFICATION ARCHITECTURE
====================================================================

The current “Product Concept & Specifications” section is too
card-heavy.

Create a structured specification area.

Recommended groups:

CONSTRUCTION - Shell material - Shell sizes - Weight - Construction type

SAFETY - Certifications - Retention - Safety standards - Rotational test
information

VISIBILITY - Visor - Sun visor - Pinlock - Tear-off compatibility

VENTILATION - Intake vents - Exhaust vents - Ventilation system

COMFORT - Liner - Cheek pads - Removability - Washability

COMMUNICATION - Speaker compatibility - Intercom compatibility - Cable
routing

Each group should disappear if no fields exist.

This prevents empty technical sections.

==================================================================== 14.
THE CIRCULAR / VISUAL METRICS NEED REVIEW
====================================================================

The screenshots show circular metric-style elements in the
specifications area.

These are visually attractive but dangerous if the values do not have a
rigorous methodology.

A circular: “75%” “83%” “95%”

immediately looks like an objective rating.

If the metric is: - shell coverage - confidence - data completeness -
safety score - comfort score

the label and methodology must be explicit.

If no methodology exists: remove the circles.

Use simple factual labels instead.

For example:

DATA CONFIDENCE High

rather than:

95%

==================================================================== 15.
“WHERE TO BUY” SHOULD BE A FIRST-CLASS SECTION
====================================================================

The buying section is much better in the Storm screenshot than the older
design.

Keep the retailer table pattern, but simplify.

Recommended:

WHERE TO BUY

Best current price ₹XX,XXX

Retailer table:

RETAILER | PRICE | AVAILABILITY | LAST CHECKED | ACTION

Example:

Amazon | ₹XX,XXX | In stock | Today | Check price Retailer B | ₹XX,XXX |
Available | 2 days ago | Check price

Do not make a retailer look available if availability is unknown.

Use: Availability unknown

rather than guessing.

Use: Last checked

for freshness.

==================================================================== 16.
PRICE HISTORY EMPTY STATE IS TOO LARGE
====================================================================

This is one of the clearest visual problems in all three screenshots.

A large buying container is followed by a huge blank “Price History”
region.

If there is no historical data, the page should NOT reserve chart
height.

Use a compact empty state:

PRICE HISTORY

Not enough historical observations yet.

Helmetsan will display price trends as more observations are collected.

That is enough.

If there is actual data: show a real chart.

The chart should include: - date - price - retailer - minimum price -
current price

Potential future: price drop alert.

But only if a real alert backend exists.

==================================================================== 17.
PRODUCT NAVIGATION
====================================================================

The current horizontal product navigation is a good idea.

However it needs to become a sticky product sub-navigation.

Recommended:

Overview Safety Fit & Sizing Specifications Where to Buy Reviews
Accessories Compare

When the user scrolls: - active section updates - navigation remains

On mobile: horizontal scrolling tabs.

Do not create too many tabs.

==================================================================== 18.
COMPARE & BUY SECTION
====================================================================

The current compare section looks like a promotional strip.

It should instead answer:

“Is there a better alternative at this price?”

Example:

COMPARE THIS HELMET

Compare Pioneer with 3 similar helmets.

[ COMPARE HELMETS ]

Suggested comparison dimensions: - Price - Certification - Weight -
Helmet type - Shell material - Visor - Riding style - verified features

A comparison recommendation should never say: “better”

without explaining why.

Use: “Similar price, different certification” “Lower listed weight”
“More verified features”

only when supported by data.

==================================================================== 19.

====================================================================

NO VERIFIED RIDER REVIEWS YET

There are no verified rider reviews for this helmet yet.

[ WRITE A REVIEW ]

Do not show: - giant empty star - 0.0 - empty bars occupying large space

When reviews exist, show: Overall rating Number of reviews Rating

==================================================================== 20.
ACCESSORIES — CURRENT SECTION IS TOO WEAK
====================================================================

The current compatible accessories section is visually small and
contains missing images.

This section has high potential because it differentiates Helmetsan from
a normal product directory.

Use:

ACCESSORIES FOR THIS HELMET

“Verified accessories and useful upgrades for this model.”

Separate into:

CONFIRMED COMPATIBLE and POTENTIAL / UNVERIFIED

Do not mix them.

Each accessory: Brand Product Type Compatibility state Price View
accessory

If no verified accessories:

NO VERIFIED ACCESSORIES FOUND

Browse all accessories or Tell us what you need

Do not display unrelated accessories simply to fill space.

==================================================================== 21.
ACCESSORY RELATIONSHIP MUST BE BIDIRECTIONAL
====================================================================

The data model should support:

Helmet -> Accessories

and:

Accessory -> Compatible helmets

This is essential.

If an accessory page says: Compatible with Pioneer

the Pioneer page must also be able to say: Compatible accessory

This should come from the same relationship table.

Do not maintain two independent lists.

==================================================================== 22.
MORE FROM BRAND — CURRENT SECTION IS TOO GENERIC
====================================================================

The current “More from [brand]” section is visually large but not highly
informative.

Cards show several products that appear visually similar but do not
explain why they are being shown.

Rename:

MORE FROM [BRAND]

and add a reason.

Possible: - Same brand - Same helmet type - Similar price

If the actual section is intended for alternatives, rename it:

SIMILAR HELMETS

Then rank by meaningful similarity.

Do not use a generic product query.

Potential cards:

SIMILAR PRICE ₹X–₹Y

SAME TYPE Full Face

ALTERNATIVE Different certification

Do not claim “best alternative” without a methodology.

==================================================================== 31.
CARD FATIGUE — MAJOR SYSTEMIC ISSUE
====================================================================

The current page puts too many things inside rounded bordered cards.

This creates: - visual fragmentation - excessive vertical lines -
dashboard feeling - low editorial hierarchy

Not every section needs a card.

Recommended pattern:

FULL-WIDTH SECTION Heading Short explanation Content

Use cards only for: - retailer offers - key facts - product
comparisons - accessories - related helmets

Use simple dividers for: - overview - specification groups - sources

Use whitespace for: - editorial sections

This will dramatically improve perceived quality.

==================================================================== 32.
VERTICAL DENSITY
====================================================================

The pages are extremely long.

The problem is not simply “too much content”.

The problem is that the page spends too much vertical space on: - empty
states - card padding - repeated headings - repeated borders - low-value
related products - large blank price history - large review empty state

Goal:

Reduce page height WITHOUT REMOVING IMPORTANT INFORMATION.

Methods: - compact empty states - better typography - two-column
technical tables - collapsible specification groups - fewer redundant
cards - horizontal related product rows - compact source information

==================================================================== 33.
TYPOGRAPHY
====================================================================

The typography currently appears too small in many sections.

Hierarchy should be stronger:

H1: Product name

H2: Major section

H3: Subsection

Body: Readable 15–17 px desktop equivalent where appropriate.

Metadata: 12–14 px.

Do not make every label tiny uppercase text.

Use uppercase only for: - eyebrow labels - metadata categories - small
utility labels

Avoid long uppercase paragraphs.

==================================================================== 34.
COLOR SYSTEM
====================================================================

Primary: Black / near-black

Background: Warm white / very light gray

Accent: Helmetsan red

Semantic: Green = verified / available Amber = uncertain Gray =
unavailable

Do not use red for everything.

Red should communicate: - primary CTA - important warnings - brand
accent

Green should communicate: - verified - compatible - in stock

Blue can be used sparingly for links / neutral informational interaction
if needed.

==================================================================== 35.
BORDER AND SHADOW SYSTEM
====================================================================

Use: 1 px neutral borders subtle radius very subtle shadow

Avoid: heavy shadows multiple nested shadows bright red borders around
ordinary sections

Red borders should mean: - alert - important decision - active action

not “this is another section.”

depending on source data.

Hero image can be larger: 4 / 3.

Related product: 1 / 1.

Accessory: 4 / 3.

==================================================================== 42.
DIFFERENT PRODUCT DATA COMPLETENESS
====================================================================

This is one of the most important improvements.

Products such as Pioneer, Storm and X3000 may have different levels of
information.

The UI should adapt.

Example:

PRODUCT A: Rich data - images - certification - fit - price -
retailers - reviews

Show full experience.

PRODUCT B: Limited data - one image - certification - basic specs - no
reviews

Show: “Limited data available”

Do not create large empty sections simply because the template expects
them.

The page should collapse gracefully.

==================================================================== 43.
INFORMATION PRIORITY MODEL
====================================================================

Every field should be assigned a priority.

P0: Certification Helmet type Price Availability Image Fit Safety

P1: Weight Shell material Retention Visor Ventilation Communication

P2: Liner details Aesthetic features secondary accessories

P3: nice-to-have metadata

If P0 data is missing, make that visible.

Do not fill the page with P3 data while P0 data is unavailable.

==================================================================== 45.
WHY THIS ORDER
====================================================================

The user first needs to identify the product.

Then: “Can I trust it?”

Safety.

Then: “Will it fit?”

Fit.

Then: “What exactly is it?”

Specifications.

Then: “Where can I get it?”

Buying.

Then: “Is there a better option?”

Comparison.

Then: “What do riders say?”

Reviews.

Then: “What else fits it?”

Accessories.

Then: “What alternatives exist?”

Similar helmets.

Finally: “Where did this information come from?”

Sources.

This is a much stronger mental model than:

database fields -> retailer -> specs -> review -> accessories.

==================================================================== 46.
“BUY” SHOULD NOT DOMINATE THE PRODUCT
====================================================================

Helmetsan is not primarily the retailer.

The platform should help the rider decide.

Therefore: “Where to buy” is important but should not visually
overwhelm: - safety - fit - comparison

Primary CTA: WHERE TO BUY

Secondary: COMPARE

Do not use: BUY NOW unless Helmetsan actually owns the transaction.

If outbound affiliate links are used: “Check price” or “View retailer”

is more accurate.

==================================================================== 47.
AFFILIATE DISCLOSURE
====================================================================

If retailer links are affiliate links: disclose this clearly.

Do not hide affiliate relationships.

Potential: “Helmetsan may earn a commission from qualifying purchases.”

Place appropriately near retailer section and footer disclosure.

==================================================================== 87.
FINAL DESIGN PRINCIPLE
====================================================================

Do not ask:

“How can we put more information on the page?”

Ask:

“What decision is the rider trying to make at this point?”

Then show the smallest amount of trustworthy information necessary to
help them make that decision.

The product page should progressively reduce uncertainty.

UNCERTAINTY ↓ IDENTITY ↓ SAFETY ↓ FIT ↓ SPECIFICATIONS ↓ PRICE ↓
COMPARISON ↓ ACCESSORIES ↓ CONFIDENCE ↓ DECISION

==================================================================== 90.
END STATE
====================================================================

A successful Helmetsan product page should feel like a trusted technical
dossier for a helmet.

The rider should be able to open a product and quickly say:

“I know what this is.” “I know what safety standard it meets.” “I know
whether it is likely to fit my needs.” “I understand the important
specifications.” “I know what it costs and where to find it.” “I can
compare it with alternatives.” “I know what accessories fit.” “I know
which information is verified.”

That is the experience Helmetsan should own.

Do not optimize for the appearance of completeness.

Optimize for trustworthy completeness.

THE CORE RULE:

EVERY PIXEL SHOULD EITHER HELP THE RIDER IDENTIFY, EVALUATE, COMPARE,
VERIFY OR ACT ON THE HELMET.

If it does none of those things, remove it.
